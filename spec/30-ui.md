# omaghy — the TUI

How `omaghy-tui` is structured, and the information-design decisions that every
surface inherits.

---

## 1. Principles

**The TUI performs no I/O.** It consumes the `Store` trait. If a surface needs
data, that is a `Store` change, not an HTTP call. This is enforced by crate
boundaries, not discipline.

**The model decides; the view draws.** Rollups, sorting, grouping, markdown
parsing, syntax highlighting, and relative-age bucketing all resolve in
`omaghy-model` (`10-domain-model.md` §1.4). A surface that computes a domain
fact is a bug — because it will compute it differently from the next surface.

**Keyboard first.** Every action is reachable by key *and* by name in the
palette. Mouse support is a convenience, never the only route to anything.

**Every state renders something honest.** Empty, stale, offline, forbidden,
and rate-limited are designed states, not fallbacks — see §8.

## 2. The app shell

One event loop selecting over three sources:

```rust
loop {
    tokio::select! {
        Some(ev) = terminal_events.next() => app.on_input(ev)?,
        Ok(ev)   = store_events.recv()    => app.on_store(ev),
        _        = tick.tick()            => app.on_tick(),   // spinners, relative ages
    }
    if app.dirty { terminal.draw(|f| app.render(f))?; app.dirty = false; }
}
```

**Render on change, not on a timer.** The tick exists only to advance spinners
and re-render relative ages; it does not drive the frame rate. Cap redraws at
~60/s so a burst of store events cannot spin the CPU.

### 2.1 Terminal restoration is non-negotiable

Raw mode plus the alternate screen means a panic that escapes leaves the user's
shell unusable — no echo, no line editing, no prompt. Therefore:

- Install a **panic hook** that restores the terminal *before* printing the
  panic, and chain to the previous hook so the message still appears.
- Restore on every exit path, including `?` propagation out of `main`.
- Handle `SIGTERM`/`SIGHUP` the same way.

A test asserts the hook is installed. This is the single most user-visible way
a TUI can misbehave, and it happens on the user's worst day.

### 2.2 Startup

Startup must reach first paint without the network. Resolve the token, open the
cache, render the dashboard from SQLite, *then* schedule refreshes. A cold start
with no cache shows the dashboard skeleton with per-section loading states — not
a blank screen, and not a modal.

## 3. Router and surfaces

Surfaces **register**; the router does not know their names at compile time.
Adding a surface must not require editing another.

```rust
pub trait Surface {
    fn id(&self) -> SurfaceId;
    fn title(&self) -> String;                       // for the header
    fn render(&mut self, f: &mut Frame, area: Rect, ctx: &Ctx);
    fn on_key(&mut self, key: KeyEvent, ctx: &Ctx) -> Outcome;
    fn on_store(&mut self, ev: &StoreEvent) -> Outcome;
    fn keymap(&self) -> &[Binding];                  // feeds help and palette
    fn on_enter(&mut self, ctx: &Ctx);               // schedule refreshes here
    fn on_leave(&mut self, ctx: &Ctx);               // cancel them here
}

pub enum Outcome { Ignored, Redraw, Push(Route), Pop, Replace(Route), Quit }
```

A surface never renders another surface, and never reaches into the router.
Navigation is expressed as `Outcome` and executed by the router.

### 3.1 Navigation is a stack

`q`/`Esc` pops. The dashboard is the root and cannot be popped. **Each entry
retains its own scroll position, filter text, and cursor** — returning from a PR
to the list you came from must land where you left, or triage becomes
unbearable.

### 3.2 Routes are addressable

```
dashboard · notifications · pr:ShaxP/shax#61 · issues:ShaxP/shax?state=open
repo:ShaxP/shax · actions:ShaxP/shax · search?q=is:pr+review-requested:@me
```

Routes are what the palette pushes, what `omaghy <route>` opens from a shell,
and what a future `omaghy watch` notification action will invoke. Parsing a
route must not require a network call.

## 4. Layout

Three zones, always:

```
┌──────────────────────────────────────────────────────────┐
│ header    title · scope · counts        viewer · sync    │  1 row
├──────────────────────────────────────────────────────────┤
│ body      the surface                                    │  flex
├──────────────────────────────────────────────────────────┤
│ footer    contextual keys          · status / toast      │  1 row
└──────────────────────────────────────────────────────────┘
```

The header carries the freshness indicator from `Fresh<T>` — the one place the
UI admits it is showing cached data. The footer shows the current surface's most
relevant bindings, never a fixed list.

### 4.1 Responsive columns

Terminal width is not negotiable the way a card's was, so **columns drop by
priority** as width shrinks:

| Width | Columns |
|---|---|
| ≥ 120 | icon · title · repo · number · state · checks · actor · age |
| ≥ 100 | icon · title · repo · number · state · checks · age |
| ≥ 80 | icon · title · repo · state · age |
| ≥ 60 | icon · title · age |
| < 60 | title · age, elided |

Title always takes the remaining space and elides right.

Widths are **terminal cells, not characters**: a CJK ideograph occupies two
cells and a combining mark none, so counting characters misaligns every column
to the right of such a title. GitHub titles contain both. Below 40 columns or 10
rows, render a single line saying the terminal is too small — do not attempt a
degraded layout nobody tested.

**A three-cell gutter precedes the first column at every width**: the cursor
marker, the unread marker, a space. Neither is a content column and neither
drops — §9 requires unread to be encoded twice, and a selection that is only
reverse video is invisible on the terminals that do not do reverse video and
in every screenshot.

> **Corrected in W1.3.** The `< 60` row read "title only", which contradicts
> §9: age "is never the column that drops", being the only always-present sort
> cue. §9 wins — it is a measured finding, and four cells is a cheap price for
> the one thing telling you which way the list is sorted.

> **Two-line rows were built and rejected.** The discarded prototype
> (`00-overview.md` §8) used them on a centred ~875px card, where they read
> well. Terminals are vertically constrained and horizontally generous, so that
> layout does not carry over: single-line rows with responsive columns are
> denser and more scannable. Two-line rows remain available via config for
> narrow terminals.
>
> **Reopened in W2.3.** That rejection was reasoned in the same medium §9 was
> measured in, so the notifications inbox ships both, switchable with `t`, for
> the owner to decide against a real terminal. See §9's note.

### 4.2 The footer cannot hold every binding — found in W2.3

`app.rs` puts **all** of `Surface::keymap()` into the footer and then drops
whole hints off the end until they fit, appending the shell's own `? help` and
`q quit` *after* them. A hundred-column terminal holds roughly six hints, so a
surface with more bindings than that silently pushes the only documented way
out of the program off the screen.

That contradicts this section's own rule — the footer shows "the current
surface's **most relevant** bindings" — and it is a real regression, not a
cosmetic one: `q` is the way out. The fix is a shell change and therefore its
own PR: either `Surface` gains a separate footer list, or `app.rs` reserves the
global hints before spending the line. Until then the notifications surface
carries `? help  q quit` on its own readout line.

## 5. Keys

Vim-shaped, and every binding is overridable in `config.toml`.

| | |
|---|---|
| `j` `k` `g` `G` `C-d` `C-u` | movement |
| `Enter` | activate · `Esc` `q` | back |
| `/` | filter within the surface |
| `:` | command palette |
| `?` | help |
| `o` | open on github.com |
| `y` | yank URL |
| `r` | refresh · `R` force refresh |
| `1`…`7` | jump to surface |
| `,` | settings |
| `r` | refresh **what this surface shows** — the surface names its own target |
| `C-c` | quit |

**The help overlay is generated from the keymap**, never hand-written — a help
screen maintained separately is a help screen that lies. Surface-local bindings
are declared in `Surface::keymap()` and appear automatically in both help and
palette.

> **`g` is on loan.** W2.3 binds `g` to the notifications grouping comparator
> (§9), so `g`/`G` are not yet top/bottom movement — `Home`/`End`/`G` stand in.
> The PR that bakes in §9's winners returns `g` to movement.

> **A surface cannot take free text.** `app.rs` resolves global keys *before*
> the surface sees them, and the globals include `q`, `r`, `o`, `:`, `?` and
> `1`–`7`. A `/` filter that accepted typed characters would therefore lose
> most of the alphabet mid-word. Until the shell gives the focused surface
> first refusal on input — a `Surface` contract change, and its own PR — `/`
> means "scope to the focused row's repository" on the notifications inbox.
> Found in W2.3.

### 5.1 The palette is the real interface

Every action carries a stable name (`notification.mark-read`,
`pr.approve`, `repo.open-in-browser`). `:` fuzzy-searches them. Anything
reachable by key must be reachable by name — that is what makes a key binding
discoverable rather than trivia, and it is what config overrides refer to.

## 6. Iconography

Octicons ship in Nerd Fonts, and every codepoint checked is present in
Omarchy's default JetBrainsMono Nerd Font. Icons are **semantic roles**, not
literal codepoints, resolved by a theme table:

`pr-open` · `pr-draft` · `pr-merged` · `pr-closed` · `issue-open` ·
`issue-closed` · `check-pass` · `check-fail` · `check-pending` · `review` ·
`comment` · `mention` · `security` · `repo` · `private`

**Every role has an ASCII fallback**, selected automatically when the terminal
or font cannot render glyphs, and forceable with `icons = "ascii"`. A user
without a Nerd Font sees `[!]` rather than a replacement box. Layout must not
shift between modes: both occupy the same cell width.

### 6.1 Verify a codepoint by glyph name, not by presence

"Every codepoint checked is present" turned out to be the wrong check. The
Octicon block is contiguous, so *every* codepoint in it is present — including
the wrong one. Seven of the fifteen roles in the P0.4 table pointed at a glyph
that existed and was not the glyph named: `pr-draft` at `oct-read`, `pr-closed`
at `oct-issue_opened`, `mention` at `oct-rocket`, `security` at `oct-eye`,
`private` at `oct-sync`, `review` at `oct-question`, `check-pending` at
`oct-verified`. All are corrected in W1.3, each carrying its Octicon name in a
comment.

The check that catches this reads the font's own `post` table, which gives
glyph *names* (`oct-git_pull_request_draft`) alongside the `cmap`. Adding a
role means looking the name up, not picking a plausible number.

**Spinners must not use braille.** Measured against the installed
`JetBrainsMonoNerdFont-Regular.ttf`: the braille block is absent entirely
(U+2801 has no glyph), confirmed independently with
`fc-list ':charset=2801'`. The conventional `⠋⠙⠹…` spinner therefore renders
as four replacement boxes on Omarchy's default font. Quadrant blocks
(`▘▝▗▖`) are present, rotate just as well, and are one cell wide.

## 7. Colour

**The 16 ANSI colours must be sufficient.** Omarchy themes the terminal, so
omaghy inherits the active theme for free (`00-overview.md` §5). Truecolor is
an enhancement, never a requirement.

Semantic roles only — never a literal colour at a call site:

`default` · `muted` · `accent` · `success` · `warning` · `danger` ·
`added` · `removed` · `selected` · `unread`

### 7.1 Never encode by colour alone

Measured, not assumed: Osaka Jade — the active theme on the development
machine — resolves `accent` and `foreground` to the same value, `#cacccc`, and
several other Omarchy themes are effectively monochrome. Anything conveyed by colour
must *also* be conveyed by glyph, position, or weight. A failing check is a
`✗` glyph that is *also* red — never red text alone.

This is equally an accessibility rule, and it is cheap if followed from the
start and expensive to retrofit.

## 8. The state matrix

Every list surface handles all of these. They are specified centrally so they
look identical everywhere, and so no surface invents its own empty screen.

| State | Renders |
|---|---|
| **Cold** — no cache | Skeleton rows plus a loading indicator. Never a blank frame. |
| **Populated** | Normally. |
| **Stale** | Normally, plus the header's freshness note. **Stale data is never hidden.** |
| **Refreshing** | Existing content plus a header spinner. Content must not be replaced by a spinner. |
| **Empty** | Why it is empty, and the most useful next action. "All caught up" is a real state that deserves design, not a shrug. |
| **Filtered to empty** | Distinct from empty — names the filter and how to clear it. |
| **Offline, with cache** | Content plus a banner naming the cause. |
| **Offline, no cache** | Empty state naming the cause, not a generic error. |
| **Rate limited** | When it resets, and that cached data is still readable. |
| **Forbidden** | You lost access; this row is not retried. |
| **Error** | What failed, in one line, plus `r` to retry. Never a stack trace. |

**A surface keeps its read errors; it does not propagate them.** Every row of
this table is a screen the surface is supposed to *draw*, so `Surface::load`
returning `Err` would tear down the whole app rather than render one of them.
It also keeps the page it already read, which is the only thing that makes
"offline, with cache" reachable at all. Recorded in W2.3, where the shell-era
placeholder did propagate.

### 8.1 The rows are not always the evidence

> **Added in W2.2.** The table above reads as though a surface's rows both
> *are* its content and *prove* a fetch happened. On the dashboard they are
> two different things, and conflating them produces a screen that lies.

A dashboard section exists because `config.toml` says so; only its **count**
comes from the store. So the number of rows is no evidence that anything was
read, and a cold cache rendered as "four sections, all empty" states as fact
something nobody has checked. A cold dashboard therefore shows the skeleton,
exactly like a cold list: what is unknown is the counts, not the sections.

Two arms consequently read differently here:

- **Empty** cannot mean "all caught up". Every section reading *nothing* is
  the good news, and it is rendered as the sections themselves — four ticks
  and four queries, because hiding them would hide what produced the good
  news. The only thing empty can mean on the dashboard is a config that
  defines no sections, which is a problem rather than a relief.
- **Filtered to empty** does not apply: the dashboard has no filter. A state
  nothing can reach does not get a screen.

> **Added when the counts became real.** There is a third thing a `0` can
> mean, and no screen can distinguish it: a query that does not match what its
> author thought. GitHub's search does not reject a bad query — a nonexistent
> repository counts 0, an invalid qualifier is silently ignored and counts
> everything. So "nothing needs your review" and "your config has a typo" are
> the same pixels, and the only defence is the one already built: the focused
> section's query is on screen verbatim, so the thing that produced the number
> can be read rather than assumed. `40-config.md` §2 carries the same warning
> where the query is written.

## 9. Information design

Measured against a real inbox and all 22 installed themes during the discarded
prototype (`00-overview.md` §8). These findings concern GitHub's data and
Omarchy's themes, so they outlived the medium that revealed them — unlike §4.1's
breakpoints, which are reasoned and unverified.

> **Settled on 2026-09-13, by looking.** W2.3 shipped the inbox with every
> alternative switchable at runtime, and the choices were made by driving it in
> a real terminal rather than by argument: `reason = glyph`, `repo = full`,
> `rows = two-line`, `triage = grey`, `group = by-repo`. All five are
> configurable — `40-config.md` §2 is now the normative statement of the
> defaults, and §5 there records what was chosen over what.
>
> **Two of them overrule this document.** `rows = two-line` overrules §4.1's
> assumption of single-line rows, which was reasoned rather than measured;
> §4.1's column priorities still govern `one-line` mode and survived the test
> unchanged. `group = by-repo` makes the grouping in this section the default
> rather than an option.
>
> **The runtime switcher is gone.** Every alternative remains implemented —
> `40-config.md` §2 makes all five configurable — but the runtime *switching*
> is not: seven key bindings, the cycling, and the readout of the current
> combination were removed once the choices were made. A variant left
> switchable for ever is a decision nobody made. Until config loading exists,
> the defaults are the surface's hardcoded initial state.

**Unread is encoded twice** — a leading marker column *and* weight — so it
survives both monochrome themes and terminals without bold.

**Age is compact and right-aligned**: `4m` `2h` `3d` `2w` `14mo`. It is the
only always-present sort cue, so it is never the column that drops. Detail views
show absolute timestamps.

**Repo names repeat, and the repetition is noise.** Measured: fourteen
consecutive rows reading `ShaxP/shax`. Mitigations, in order:
elide the owner when it matches the viewer; elide the repo entirely when every
visible row shares it (naming it in the header instead); offer grouping under
section headers.

**Reason is a glyph, not a word.** Twelve notification reasons cannot each own
a colour when a theme may supply one accent. Glyph plus position carries it;
the full word appears in the detail view and on the focused row.

> Measured in W2.3: **no column is wide enough for the word.** `Column::State`
> is eight cells, of which a glyph and a separator take two, so "review
> requested" has six cells to live in. A reason rendered as text is therefore
> an abbreviation (`review`, `@team`, `subbed`) whichever way the comparison
> goes — which is evidence for the glyph, and is why the focused-row line is
> not optional.

**Triage keeps the row.** Marking read updates in place rather than removing —
a list that reflows under the cursor makes bulk triage error-prone. `u` filters
to unread when a clean sweep is wanted.

## 10. Testing

Snapshot tests via ratatui's `TestBackend`, driven by `FakeStore`
(`20-store.md` §8). **Every surface ships snapshots for every applicable row of
§8** — the error states are the ones that rot unnoticed, and they are most of
what a user sees on a bad day.

Also snapshotted: each width breakpoint in §4.1, and both icon modes from §6.

Snapshots contain no timestamps, no durations, and no ordering that depends on
a hash map, or they will fail on Tuesdays for reasons nobody can reproduce.
